# showcase/

Game assets in this folder were drawn **through the advertised MCP tool surface only** — spawned
`packages/mcp/dist/cli.js` as a child process, raw JSON-RPC over stdio, nothing else. No
`@pixel/core` import, no `Editor`, no library shortcut. `scripts/showcase-build.mjs` and every
`ops.json` here hold to that on purpose: the point of a showcase is to prove the tool list is
enough, and a piece that needed a library import would prove nothing and would not replay
anywhere.

Each piece directory carries the complete recipe, so a third party can land on the same bytes:

```
showcase/<piece>/
  ops.json            the exact ordered advertised tool calls, [{label, tool, arguments}]
  manifest.json       per-call measurements + output hashes (generated by `showcase-build run`)
  <piece>.pixel       the editable source the server wrote
  out/                the rendered outputs, byte-stable
  README.md           what the piece is and the decisions behind it
```

## Reproduce

From the repository root:

```bash
node scripts/showcase-build.mjs run <piece> --verify
```

`run` replays `ops.json` against one fresh server, writes `manifest.json`, and with `--verify`
replays a **second** time and byte-compares every file in `out/`. A piece that does not reproduce
fails the command rather than quietly writing different bytes.

The stock harness works too, and is the one to use if you want to see the raw responses:

```bash
node scripts/mcp-call.mjs calls showcase/<piece>/ops.json
```

Both write to the same paths, so the hashes match either way. Run from the repo root: an op's
destination is a relative path and resolves against the caller's working directory.

## Explore the surface

```bash
node scripts/showcase-build.mjs tools                  # the 36 advertised tools
node scripts/showcase-build.mjs probe <file.json>      # ad-hoc [{tool, arguments}] against a live server
node scripts/showcase-build.mjs probe <file.json> --quiet   # one line per call, for iterating
```

`probe` is the draw-look loop: it holds one session open, so a document created in step 0 is
still there in step 7. Add an `export_png` op pointing anywhere on disk and open the result.

## What is and is not reproducible

Everything under `out/` is **byte-identical** across runs and across harnesses. That is what
`--verify` gates on.

The `<piece>.pixel` container is **not** byte-stable, and that is an observation about the engine
rather than about this folder: the container and the export manifest embed session-generated
frame and document ids (`frm_…`, `doc_…`), so their bytes move even when the artwork does not.
The PNGs do not, because nothing session-specific reaches them. `manifest.json` records this
explicitly under `source.byteStable` instead of pretending otherwise.

`manifest.json` is also the only file here that is a *measurement* rather than an output, so its
`wallClockMs` moves run to run. Its `argumentBytes` block is byte-identical every run; its
`resultBytes` moves by a couple of dozen bytes, because the response envelope echoes the
session-assigned `document.id` and that string's length is not fixed. `files` never moves.
